# Код-стайл

## Язык

Вся документация и все комментарии в проекте пишутся **на русском языке**. Это распространяется на:

- документирующие комментарии (JSDoc, rustdoc);
- обычные строчные и блочные комментарии в коде;
- пояснительные комментарии в конфигурационных файлах (`nuxt.config.ts`, `.gitignore` и т.п.);
- файлы документации в `docs/` и `README.md`.

Исключение — идентификаторы кода (имена переменных, функций, типов, ключей API), которые остаются на английском.

## Имена файлов

Имена файлов и директорий должны быть на английском языке, без транслита и кириллицы.
Для составных имен используется `kebab-case`: например, `reviews.vue`,
`paint-shop-4.jpg`, `short-sawmill-video.mp4`.

Документирующие комментарии пишутся по фиксированной структуре.
Ниже — правила и эталонные примеры для TypeScript и Rust.

## Тестирование публичного API

Каждая публичная функция API должна быть покрыта тестами. Под публичной функцией API
понимается экспортируемая функция, обработчик, сервисный метод или другая точка входа,
которая формирует внешний контракт frontend или backend.

Тесты должны покрывать все значимые сценарии поведения:

- успешное выполнение;
- ошибки и некорректные входные данные;
- граничные значения;
- пустые и отсутствующие значения, если они допустимы типами или контрактом;
- побочные эффекты и изменение состояния, если функция их выполняет;
- формат возвращаемых данных и коды ошибок для HTTP API.

Если полный перебор вариантов невозможен или нецелесообразен, в тестах фиксируются все
сценарии, влияющие на контракт функции, а пропущенные случаи явно объясняются в описании
теста или рядом с тестовым набором.

## Работа с базой данных в Rust API

Для backend на Rust основная ORM проекта — **SeaORM**. CRUD-логика должна использовать
entity, ActiveModel и Entity API SeaORM. Ручной SQL допустим для схемы, миграций и
точечных запросов, когда ORM-выражение делает код менее понятным; такие исключения
нужно фиксировать рядом с кодом или в документации.

## Ошибки в Rust API

Ошибки backend должны описываться явными enum-ами, а не `String`/`&str` как типом ошибки.
Каждый вариант enum-а отражает отдельный сценарий: например, неверный формат Basic Auth,
пустой payload, недопустимый рейтинг, отсутствие записи или ошибка БД.

Публичные HTTP-ответы об ошибках возвращают только понятное поле `message`; категория ошибки
определяется HTTP-статусом и внутренним enum-вариантом. Строки допустимы как пользовательское
сообщение ответа или контекст внутри варианта enum-а, если он нужен для диагностики.
Одинаковые сообщения выносятся в константы, чтобы не дублировать их в обработчиках.

## Rust (rustdoc)

1. Однострочное описание.
2. `# Параметры` — список `- \`имя\` - описание`.
3. `# Errors` — список `- [\`ТипОшибки\`] в случае ...`.
4. `# Возвращаемое значение` — описание результата.

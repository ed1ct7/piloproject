# SEO под Яндекс: требования на уровне кода

Правила, чтобы страницы хорошо индексировались и ранжировались в поиске Яндекса:
техническая база (разделы 1–8), факторы ранжирования за пределами кода (раздел 9),
стратегия доменов и хостинга (разделы 10–11), порядок проверки и сроки (раздел 12),
редизайн после запуска (раздел 13).
Примеры даны под стек проекта — **Nuxt 3 в режиме SSG** (статический HTML краулится лучше всего).

## 1. Семантика и структура страницы

- **Один `<h1>` на страницу.** Дальше иерархия `h2 → h3` без перескоков уровней.
- Семантические теги-ориентиры: `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<footer>`.
- Обязательно указывать язык: `<html lang="ru">`.
- У каждого `<img>` — осмысленный атрибут `alt`.
- Уникальные `<title>` и `<meta name="description">` на каждой странице.

## 2. Мета-теги

В Nuxt задаются через `useSeoMeta` / `useHead`:

```ts
useSeoMeta({
  title: 'Пиломатериалы в Разбегаево — доска, брус',
  description: 'Пиломатериалы от производителя оптом и в розницу. Доставка по СПб и ЛО.',
  ogTitle: 'Пиломатериалы в Разбегаево',
  ogDescription: '...',
  ogImage: `${siteUrl}/images/og-cover.jpg`,
  ogType: 'website',
})

useHead({
  htmlAttrs: { lang: 'ru' },
  link: [{ rel: 'canonical', href: `${siteUrl}/tovary/doska` }],
})
```

- **`canonical`** на каждой странице — защищает от дублей. Строить только от `siteUrl`
  из `frontend/utils/seo-routes.ts`, не строкой.
- `robots: 'index, follow'` писать не нужно — это дефолт; директива нужна только для
  закрытия (`noindex`).
- `viewport` Nuxt добавляет сам; мобильная адаптивность учитывается в ранжировании.
- **Favicon** — показывается в выдаче Яндекса рядом со сниппетом и влияет на CTR;
  `ogImage` — превью при шаринге в мессенджерах и соцсетях.

## 3. Микроразметка Schema.org (JSON-LD)

Яндекс активно использует структурированные данные. Для организации — тип `LocalBusiness`:

```ts
useSchemaOrg([
  defineLocalBusiness({
    '@id': `${siteUrl}/#localbusiness`,
    '@type': 'HomeAndConstructionBusiness',
    name: 'Пилорама Разбегаево',
    url: `${siteUrl}/`,
    telephone: '+7...',
    address: {
      '@type': 'PostalAddress',
      addressLocality: 'Разбегаево',
      addressRegion: 'Ленинградская область',
      addressCountry: 'RU',
    },
  }),
})
```

Другие полезные типы:
- `Product` + `Offer` — карточки товаров. Без поля `price` товарная разметка почти не даёт
  расширенных сниппетов — размечать цены, как только они появятся на страницах (цены
  обязательны и как коммерческий фактор, раздел 9).
- `BreadcrumbList` — хлебные крошки.

> **Внимание, `aggregateRating`:** размечать рейтинг можно только там, где отзывы и оценка
> реально видны пользователю на странице, и только из реальных данных — не константами
> (identity-разметка LocalBusiness сайтвайд, а отзывы видны только на `/otzyvy`, поэтому
> в identity рейтинга нет). Разметка рейтинга без видимых отзывов считается манипуляцией
> структурированными данными — Яндекс и Google такую разметку игнорируют или наказывают.
> Отзывы на `/otzyvy` пререндерятся в статический HTML на этапе `npm run generate`
> (см. раздел 9), поэтому если добавлять рейтинг — только на этой странице и с подсчётом
> из загруженных отзывов.

В проекте разметка ведется через `nuxt-schema-org`, а не ручной JSON-LD в `useHead`.

## 4. Региональность и геозависимое ранжирование

Для локального бизнеса (пилорама, доставка по СПб и ЛО) — один из **главных** факторов: большинство коммерческих запросов геозависимы, Яндекс показывает пользователю ответы из его региона. Без привязки к региону сайт не попадёт в локальный топ, сколько ни оптимизируй вёрстку.

- **Присвоение региона в Вебмастере** — раздел «Информация о сайте → Региональность». Яндекс часто **не** определяет регион автоматически, поэтому задаётся вручную. Основной регион здесь — Санкт-Петербург и Ленинградская область.
- **Яндекс Бизнес** (бывш. Справочник): карточка организации с адресом, телефоном, часами работы. Подтверждает регион, даёт присутствие в Картах и локальной выдаче.
- **Региональный телефон + физический адрес** на каждой странице (футер + `LocalBusiness`-разметка из раздела 3). Несколько точек → перечислить все адреса, тогда сайту присвоят несколько регионов.
- **Региональные посадочные страницы (геолендинги)** — отдельная страница под каждый реальный город/район присутствия и доставки: «Пиломатериалы в Гатчине», «Доставка в Пушкин» и т. п. Требования к каждой:
  - уникальный контент (не шаблон с автоподстановкой топонима), локальные цены и условия доставки;
  - свои `<title>`, `description`, `<h1>` с названием региона;
  - `canonical` на саму себя;
  - `LocalBusiness`-разметка с полем `areaServed`.

```ts
// на геолендинге дополняем LocalBusiness зоной обслуживания
areaServed: [
  { '@type': 'City', name: 'Гатчина' },
  { '@type': 'City', name: 'Пушкин' },
],
```

- **Структура для мульти-регион**: поддомены (`spb.site.ru`) — каждый привязывается к своему региону в Вебмастере **отдельно**; либо папки (`site.ru/spb/`). Для одного региона поддомены не нужны — хватает геолендингов в общей структуре.
- **Не клонировать** одну страницу под десятки городов с заменой названия — Яндекс считает это дорвеями и переоптимизацией: риск дорвей-фильтра и «Баден-Бадена» (фильтр за переоптимизированные тексты). «Минусинск» — отдельный фильтр за покупные SEO-ссылки, к геолендингам он отношения не имеет. Страницы делать только под регионы, где реально есть присутствие или доставка.
- Мета-теги `geo.region` / `geo.placename` Яндекс **не** учитывает — регион берётся из Вебмастера, Бизнеса и разметки.

## 5. robots.txt (специфика Яндекса)

```
User-agent: *
Allow: /
Sitemap: https://site.ru/sitemap.xml

# Clean-param — директива ТОЛЬКО Яндекса: склеивает URL с мусорными GET-параметрами
Clean-param: utm_source&utm_medium&sort /
```

- **`Clean-param`** — уникальная директива Яндекса, убирает дубли по GET-параметрам. Google её игнорирует.
- **`Host`** — устарела, Яндекс перестал её учитывать (~2018). Вместо неё — 301-редирект + `canonical` на главное зеркало.
- В проекте `robots.txt` генерируется модулем `@nuxtjs/robots` из `frontend/nuxt.config.ts`; ручной файл в `frontend/public` не нужен.
- Служебные страницы `/admin` и `/system-status` закрыты от индексации и не должны попадать в sitemap.

## 6. sitemap.xml

Карта сайта со всеми индексируемыми URL. В текущей конфигурации проекта она генерируется
модулем `@nuxtjs/sitemap` из списка `indexableRoutes` в `frontend/utils/seo-routes.ts`.
Этот же список используется для SSG-пререндеринга в `frontend/nuxt.config.ts`, чтобы
публичные страницы и sitemap не расходились между собой.

Для статической сборки Nuxt дополнительно есть:

- `frontend/server/plugins/sitemap-sources.ts` — передает `indexableRoutes` в `@nuxtjs/sitemap`;
- `frontend/modules/static-sitemap.ts` — явно добавляет `sitemap.xml` в пререндер.

После добавления новой индексируемой страницы ее URL нужно добавить в `indexableRoutes`,
проверить `npm run generate` и загрузить обновленную карту в Яндекс.Вебмастер.

## 7. Яндекс.Вебмастер и ускорение индексации

Подтверждение прав — мета-тег на всех страницах (в Nuxt — через `app.head` в
`nuxt.config.ts`, чтобы попал в каждую страницу):

```ts
app: {
  head: {
    meta: [{ name: 'yandex-verification', content: '<код из Вебмастера>' }],
  },
},
```

Альтернативы: HTML-файл в корне сайта или TXT-запись в DNS (удобно, когда мета-тег
добавить нельзя).

После подтверждения: залить sitemap, отслеживать индексацию, ошибки обхода и ИКС
(индекс качества сайта).

Ускорение индексации (без этого новые страницы ждут планового обхода):

- **«Переобход страниц»** в Вебмастере — вручную отправить URL на переиндексацию
  (лимит в сутки зависит от сайта). Использовать после запуска и после правок ключевых страниц.
- **IndexNow** — протокол мгновенного оповещения поисковика о новых/изменённых URL,
  Яндекс поддерживает нативно. Требуется ключ: текстовый файл `<ключ>.txt` с ключом
  внутри в корне сайта (в проекте — положить в `frontend/public/`), без него запросы
  к API отклоняются. Для Nuxt-SSG проще всего дёргать API после деплоя.
- **«Обход по счётчикам»** в Вебмастере — разрешить Яндексу узнавать страницы из данных
  Метрики (см. раздел 9): бот приходит на страницы, где были посетители, не дожидаясь sitemap.

## 8. Производительность

Яндекс учитывает скорость и стабильность страницы не меньше Google.

- **Core Web Vitals**: LCP, CLS, INP.
- Ленивая загрузка изображений: `loading="lazy"`; современные форматы WebP/AVIF генерируются через `@nuxt/image`.
- Для SSG критичные изображения главной и страницы отзывов готовятся в два шага внутри `npm run generate`:
  `frontend/scripts/prepare-static-images.mjs` создает WebP-исходники, а
  `frontend/scripts/generate-static-images.mjs` создает статические `_ipx`-варианты из HTML.
- SSG уже даёт быстрый первый рендер — плюс к оценке.
- Обязательны HTTPS и ЧПУ-URL (`/tovary/doska`, а не `?id=123`).
- **Mobile-first**: с 2024 года основной робот Яндекса — мобильный: индекс строится по
  мобильной версии страниц, в том числе для десктопной выдачи. Весь контент, мета-теги и
  разметка должны присутствовать в мобильной вёрстке; «урезанная мобилка» = урезанный
  индекс. Проверять страницы в первую очередь на мобильном вьюпорте (Lighthouse mobile,
  DevTools device toolbar).

## 9. За пределами кода: коммерческие и поведенческие факторы

Разделы 1–8 — техническая гигиена: она даёт допуск в выдачу, но не высокие позиции.
По исследованиям ранжирования, в коммерческой выдаче Яндекса 60–70 % веса дают
коммерческие и поведенческие факторы. Что это значит для сайта пилорамы:

### Коммерческие факторы (что должно быть на страницах)

- **Цены** — у каждой товарной позиции, в явном виде. Страница «Пиломатериалы» без цен
  проигрывает конкуренту с прайсом при прочих равных.
- **Телефон и адрес** — на каждой странице (шапка/футер), регион в коде города.
- **Условия доставки** — отдельная страница с зонами, сроками и стоимостью (есть: `/dostavka`).
- **Отзывы** — видимые на сайте, не только в карточке Яндекс Бизнеса. Отзывы с `/otzyvy`
  пререндерятся в статический HTML при `npm run generate` (запрос к backend API на этапе
  сборки), поэтому поисковик видит их без JavaScript. Чтобы отзывы попали в сборку,
  backend должен быть доступен по `NUXT_PUBLIC_API_BASE` в момент генерации; свежие
  отзывы попадают в HTML при каждой пересборке.
- **Ассортимент** — отдельные страницы под товарные группы (доска, брус, и т. д.), а не
  один общий список: страница = кластер запросов.
- **Реквизиты и доверие** — ИНН/ОГРН, юридическое название, страница «О компании».
  Для Яндекса это сигнал реального бизнеса; сайты без реквизитов проигрывают в
  коммерческом ранжировании.

### Поведенческие факторы и Яндекс.Метрика

- Яндекс измеряет: клики в выдаче, возвраты к поиску, время и глубину на сайте.
  Накрутка карается, единственный устойчивый способ влиять — контент, который отвечает
  на запрос, и быстрый удобный сайт (разделы 1 и 8).
- Медленная загрузка → отказы → падение позиций: скорость влияет дважды, напрямую и
  через поведение.
- **Поставить Яндекс.Метрику с первого дня**: это инструмент измерения поведенческих
  (отказы, время, глубина, конверсии — звонки/заявки) и источник данных для
  «Обхода по счётчикам» в Вебмастере (раздел 7). Без Метрики поведение на сайте
  не видно ни владельцу, ни в полной мере Яндексу. Счётчик подключать асинхронно,
  чтобы не портить LCP; вебвизор — по желанию.

### Семантика

- Список страниц должен расти из семантического ядра (Яндекс Wordstat), а не наоборот:
  сначала кластеры запросов («брус 150х150 купить», «доска обрезная спб цена»,
  «пиломатериалы гатчина»), потом — страница под каждый кластер.
- Новые страницы добавлять в `indexableRoutes` (раздел 6).

### Карточка Яндекс Бизнеса

- По геозапросам блок Карт часто стоит выше органики — рейтинг и наполнение карточки
  работают наравне с сайтом. Карточку вести параллельно: фото, прайс, ответы на отзывы,
  актуальные часы работы. Сайтом организации в карточке указывать основной домен.

## 10. Домены: свой сайт и визитка Яндекс Бизнеса

Текущее состояние: у организации есть автоматическая визитка Яндекс Бизнеса
(`pilorama-razbegaevo.clients.site`). Этот сайт из репозитория запускается **отдельно,
на собственном домене** — визитка остаётся жить параллельно.

- **Переезд с визитки невозможен**: на `clients.site` нельзя настроить 301-редирект —
  сервером управляет Яндекс. Поэтому схема «отдельный новый сайт» — единственный вариант,
  накопленное визиткой не переносится.
- По официальной справке Яндекс Бизнеса визитка и собственный сайт «работают параллельно,
  не конкурируя». Визитку можно вручную снять с публикации в кабинете, если она начнёт
  перебивать основной сайт в выдаче (обратимо).
- **Аффилиат-фильтр**: сайты одной тематики в одном регионе с общим телефоном/адресом/
  названием Яндекс группирует и показывает по запросу один. Чтобы выбирался основной сайт,
  а не визитка: уникальные тексты (не копировать с визитки — совпадение контента и
  структуры решает склейку не в нашу пользу) и полнота сайта (у полноценного сайта
  с ценами и страницами почти всегда преимущество перед одностраничной визиткой).
- После запуска в карточке Яндекс Бизнеса в поле «Сайт» указать основной домен.

**Перед запуском обязательно** поменять `siteUrl` в `frontend/utils/seo-routes.ts`:
сейчас там адрес визитки. `siteUrl` — единственный источник домена: из него собираются
canonical на страницах (`useHead` импортирует его), sitemap, robots и `@id` разметки.
Если запустить сайт со старым значением, каждая страница будет сообщать Яндексу, что её
«настоящая» версия живёт на визитке, и новый домен не проиндексируется. CSP в
`nuxt.config.ts` подставляет `siteUrl` автоматически; вручную обновить остаётся только
`ALLOWED_ORIGINS` backend. Новые страницы обязаны строить canonical от `siteUrl`, а не строкой.

**Чеклист зеркал при запуске нового домена** (сделать до первой индексации, потом склейка
зеркал занимает недели):

1. Выбрать главное зеркало: `www` или без `www` (обычно без).
2. 301-редиректы на главное зеркало: `http → https` и `www → без-www` (или наоборот) —
   на реверс-прокси.
3. Слэш-дубли: статический хостинг часто отдаёт `/dostavka` и `/dostavka/` оба со статусом
   200. Canonical это прикрывает, но чище — 301 на один вариант на реверс-прокси.
4. В Вебмастер добавлять сразу главное зеркало (https, выбранный вариант www).

## 11. Хостинг с точки зрения SEO

География сервера на ранжирование почти не влияет — регион задаётся в Вебмастере и
Бизнесе (раздел 4), а не по IP. Что влияет:

- **Аптайм — главное.** Повторяющиеся таймауты и 5xx при обходе → страницы выпадают из
  индекса, ИКС проседает. Домашний ПК с туннелем прода не тянет именно из-за этого.
- **Доступность из РФ.** Зарубежные подсети попадают под блокировки РКН «за соседа»;
  Cloudflare-проксирование периодически замедляется на ТСПУ; часть западных хостеров
  сами режут РФ-трафик. Для аудитории СПб/ЛО — VPS в РФ.
- **TTFB до аудитории**: РФ ~5–20 мс, Европа ~50–80 мс — влияет на Core Web Vitals
  и поведенческие.
- YandexBot должен беспрепятственно доходить до сайта (не резать РФ-подсети файрволом).
- Не SEO, но рядом: отзывы содержат персональные данные (`authorName`) — по 152-ФЗ
  хранение ПД граждан РФ должно быть на серверах в РФ.

**Тестовые стенды** (домашний ПК + туннель — годится): любой публичный тестовый домен
закрывать от индексации, иначе Яндекс проиндексирует его как дубль и склеит зеркала.
На реверс-прокси стенда:

```
header X-Robots-Tag "noindex, nofollow"
```

## 12. Что и где проверяется, сроки

| Уровень | Что | Где проверяется |
|---------|-----|-----------------|
| Техника | вёрстка, мета, разметка, sitemap, скорость | локально: `npm run generate` + Lighthouse + валидатор микроразметки |
| Индексация | обход бота, страницы в индексе, ошибки | только боевой домен + Вебмастер |
| Ранжирование | позиции, трафик | только боевой домен + время |

У поиска нет «песочницы»: любой индексируемый домен — уже боевой. Ориентиры по срокам:
страницы в индексе — дни–3 недели; регион присвоен и позиции устаканились — 1–3 месяца,
по конкурентным коммерческим запросам дольше. Сроки попадания в индекс сжимаются
инструментами из раздела 7: «Переобход страниц», IndexNow, «Обход по счётчикам» —
с ними новые страницы попадают в индекс за часы–дни вместо недель; на скорость набора
позиций они не влияют. SEO-процесс итеративный: запуск → Вебмастер → смотреть
обход/индекс/запросы → править → ждать.

## 13. Редизайн после запуска

Запускаться до финального дизайна — правильно: часы индексации, региона и возраста
домена тикают месяцами, а дизайн меняется в любой момент. Яндекс ранжирует не
«красоту», а контент, структуру, мету и поведение пользователей: CSS, сетка,
картинки, шрифты, порядок блоков — невидимы для индекса, менять свободно.

Что при редизайне ломать нельзя:

1. **URL страниц** — не переименовывать без 301-редиректа. Смена адреса без
   редиректа = страница выпадает из индекса и индексируется заново с нуля.
2. **`title`, `description`, `h1`, тексты** — менять можно, но осознанно: любое
   изменение — пересчёт релевантности, позиции пару недель колеблются. Массово
   не перетряхивать без причины.
3. **Контент в HTML** — не уносить тексты и отзывы в клиентский JS: всё значимое
   должно оставаться в статическом HTML (ради этого отзывы пререндерятся, §9).
4. **Мобильная вёрстка** — новый дизайн не должен урезать мобильную версию (§8,
   mobile-first: индекс строится по ней).
5. **Скорость** — тяжёлые шрифты/скрипты/картинки не завозить без оптимизации;
   после каждой итерации дизайна проверять LCP/CLS в Lighthouse mobile (§8).
6. **Семантика** — один `h1`, иерархия `h2 → h3`, `alt` у изображений — не терять
   при перевёрстке (§1).

Оговорка: не запускать откровенно сырое. Поведенческие факторы пишутся с первого
дня — если ранние посетители массово уходят, это накопленный минус. «Доводить
дизайн после запуска» ≠ «запустить черновик».
